## Принципы ООП — обязательно демонстрировать

Проект — экзаменационная работа. Каждый принцип должен быть виден в коде явно.

### Наследование
Иерархия идёт строго сверху вниз:
```
GameObject → Entity → Player
                    → Zombie → WalkerZombie
                             → RunnerZombie
                             → SpitterZombie
                    → Boss   → PatientZeroBoss
```
- Новые типы врагов — всегда через наследование от `Zombie`, не копипаст
- Никогда не наследоваться от двух классов сущностей одновременно

### Инкапсуляция
- Поля здоровья, опыта, голода — **всегда приватные** (`_health`, `_xp`)
- Доступ только через `@property` и методы (`take_damage()`, `heal()`)
- Изменение приватного поля напрямую извне — ошибка архитектуры
```python
# правильно
player.take_damage(10)
print(player.health)

# неправильно
player._health -= 10
```

### Полиморфизм
- Все враги обновляются через `enemy.update(dt)` — единый вызов, разное поведение
- Метод `attack()` переопределяется в каждом подклассе
- Не использовать `isinstance()` для выбора поведения — это нарушение полиморфизма

### Композиция
- `Player` содержит системы как поля: `self.inventory`, `self.health`, `self.hunger`
- Системы не наследуются — они подключаются
- Если логика не связана напрямую с сущностью — выноси в отдельную систему

## Архитектурные правила

### EventBus — главный способ связи систем
```python
# эмитить событие
EventBus.emit("entity_damaged", {"target": self, "amount": 10})

# подписаться
EventBus.on("entity_damaged", self._on_damage)
```
- **Запрещено** импортировать `HUD` в `Player` или `CombatSystem` в `Quest`
- Все побочные эффекты (звук, UI, квесты) — через события, не прямые вызовы

### Данные — через JSON, не хардкод
- Статы врагов, урон оружия, HP босса — в `assets/data/*.json`
- В коде — только загрузка и использование, никаких магических чисел
```python
# правильно
self.damage = config["damage"]

# неправильно
self.damage = 25
```

### Константы — только в settings.py
```python
# правильно
from settings import FPS, SCREEN_W, SCREEN_H

# неправильно
clock.tick(60)
screen = pygame.display.set_mode((1280, 720))
```

### Экраны — через стек состояний
```python
state_manager.push(InventoryUI())   # открыть
state_manager.pop()                  # закрыть, вернуться к предыдущему
```
- Не использовать булевы флаги `is_paused`, `show_inventory`

## Стиль кода

- **Язык кода:** английский (имена классов, методов, переменных, комментарии в коде)
- **Язык документации:** русский (docstring, CLAUDE.md, README)
- Type hints обязательны для всех публичных методов
- Docstring на каждом классе — минимум одна строка

## Порядок разработки (итерации)

При добавлении нового функционала соблюдай порядок слоёв:

```
1. data/       → определи структуру данных (@dataclass)
2. core/       → расширь базовый класс если нужно
3. entities/   → реализуй конкретный объект
4. systems/    → добавь логику системы
5. ui/         → отобрази в интерфейсе
```

Никогда не начинай с UI — UI всегда последний.

## Запрещено в этом проекте

- `import pygame` вне `main.py`, `settings.py` и классов, которые явно работают с рендером
- Прямые вызовы между системами в обход EventBus
- Глобальные переменные вне `settings.py`
- Логика геймплея внутри UI-классов
- `print()` для отладки в продакшн-коде — использовать `logging`
- Процедурная генерация карт (вне скоупа v1)
- Крафт, строительство базы, мультиплеер (вне скоупа v1)
